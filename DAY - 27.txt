- Traditional Networks vs. Controller-Based Networks (SDN) — CCNA

  1. What is a Traditional Network?
     - In a traditional network, each device (switch, router, firewall) must be configured manually — one-by-one, CLI-by-CLI.
     - Each device has its own brain (control plane and data plane are together).
     - No central control — devices decide by themselves (distributed control).
     - Example:
       - If you want to add a VLAN to 50 switches, you must log in to each switch and configure manually!
	   
  2. What is a Controller-Based Network (SDN)?
     - In a controller-based network, you have a central controller that controls all network devices.
     - The controller communicates with routers and switches via APIs (example: OpenFlow, NETCONF, RESTCONF).
     - The devices (switches, routers) become simple forwarding devices — brains move to the controller!
     - Example:
       - You create a VLAN once in the controller → and it automatically configures all switches.
       - This concept is called Software Defined Networking (SDN).
	   
  - Why do we need Controller-Based Networks?
    Problem in Traditional	                  How Controller-Based Network Helps
    Manual configuration takes time.	      Central controller automates changes.
    High chances of human error.	          Automation reduces human mistakes.
    Hard to scale (adding devices is slow).	  Easy to scale — add new devices quickly.
    Hard to monitor whole network.	          Controller has full network visibility.
    Troubleshooting is slow.	              Instant visibility and problem detection.
	
  - Key Components:
    Component	       Description
    Controller	       Brain of the network (e.g., Cisco DNA Center, APIC-EM).
    Network Devices	   Switches, routers act like simple machines (forwarding only).
    Southbound APIs	   Communication from controller to devices (OpenFlow, NETCONF).
    Northbound APIs	   Communication from controller to applications (REST APIs).
	
  - Major Benefits of Controller-Based Networks:
    - Speed: Quickly configure hundreds of devices.
    - Security: Better centralized security policies.
    - Automation: Less manual work, more auto-configuration.
    - Visibility: See entire network in one dashboard.
    - Scalability: Easier to grow networks without headache.
    - Better Troubleshooting: Faster fault detection and correction.

- What is SDN (Software Defined Networking)

- In CCNA, SDN (Software Defined Networking) is introduced as a modern networking architecture where the control plane is separated from the data plane and is managed 
   centrally by software.

- What is SDN?
  - Software Defined Networking (SDN) is a networking approach where:
    - Control Plane (decision-making about where traffic should go) is handled by a central controller (software).
    - Data Plane (actual forwarding of packets) remains in the networking devices (switches, routers).

  - Instead of configuring each switch or router individually (CLI on each device), you configure a central SDN controller — and it pushes the configuration to all devices.


- Why SDN is Important in CCNA
 - Traditionally:
   - Every switch/router had its own control plane.
   - Network changes had to be done manually on each device.
 
 - With SDN:
   - One central controller programs all devices.
   - Easier automation, scalability, and policy-based control.


- Key Components in SDN (CCNA Level)
  1. Application Layer
    - Applications request network resources and policies (e.g., firewall rules, QoS settings).
    - Examples: Network management apps, monitoring tools.

  2. Control Layer
    - The SDN Controller (brain of the network).
    - Makes decisions about traffic flow and pushes them to network devices.
    - Example: Cisco DNA Center, OpenDaylight.

  3. Infrastructure Layer
    - Physical switches, routers, and other devices that forward traffic.
    - Receive instructions from the controller via Southbound APIs (like OpenFlow).


- How SDN Works
  1. Network Admin tells the SDN controller the desired policies (e.g., “Allow HTTP, block FTP”).
  2. Controller translates policies into actual device configurations.
  3. Southbound API sends instructions to network devices.
  4. Devices forward packets as instructed (data plane).
  5. Northbound APIs allow apps and automation tools to communicate with the controller.

- Example in CCNA Terms
 - Without SDN:
   Switch1> conf t
   Switch1(config)# vlan 10
   Switch1(config)# exit
   Switch2> conf t
   Switch2(config)# vlan 10
 - You repeat on all devices.

 - With SDN:
   - You tell the controller: "Create VLAN 10 on all switches."
   - Controller pushes config to all switches instantly.

- Why We Use SDN
  - Centralized control instead of device-by-device configuration.
  - Automation → Faster deployment of network changes.
  - Programmability → Integrate with scripts and APIs.
  - Scalability → Manage hundreds of devices easily.
  - Policy-based management → Define rules once, apply everywhere.

- CCNA Tip: You don’t configure full SDN in CCNA labs — you mostly need to understand:
  - What SDN is
  - The concept of control plane vs data plane
  - The role of APIs (Northbound & Southbound)
  - Benefits over traditional networking

       │   Application Layer        │
       │ (Network Apps, Monitoring, │
       │   Security Policies)       │
       └───────────▲────────────────┘
                   │ Northbound API (REST API)
                   ▼

- How it works step-by-step:
  1. Application Layer – Admins or automation scripts tell the network what they want
     (e.g., "Block all FTP traffic, allow HTTP").

  2. Control Layer (SDN Controller) – The brain of the network, translates these requests into network device instructions.
  3. Infrastructure Layer – Actual routers, switches, and APs receive the instructions and forward traffic accordingly.

- What is Control Plan and Data Plan in router.

1. Control Plane
  - Definition:
    - The control plane is the brain of the network device.
    - It decides where to send packets but doesn’t actually move them.

  - Main Jobs in a Router/Switch:
    - Routing protocols (OSPF, EIGRP, BGP) → Build routing tables.
    - Switching logic (MAC address table learning).
    - Spanning Tree Protocol (STP) decisions.
    - ARP / Neighbor Discovery.
    - Updates the forwarding table for the data plane.

  - Where it runs:
    - On the CPU of the device.

- Example in Cisco Router:
  - Router receives a packet for 10.1.1.0/24.
  - The control plane looks at the routing table and decides "Next hop is 192.168.1.1 via Gig0/1".
  - It programs the CEF (Cisco Express Forwarding) table so the data plane can forward future packets instantly.


2. Data Plane
  - Definition:
    - The data plane (also called forwarding plane) is the muscle of the network device.
    - It actually moves packets from the incoming interface to the outgoing interface based on the forwarding table prepared by the control plane.

- Main Jobs:
  - Forwarding packets at high speed.
  - Applying ACLs (Access Control Lists) for filtering.
  - Applying QoS (Quality of Service) rules.
  - Encapsulation/decapsulation.

- Where it runs:
  - In ASIC hardware chips or fast-path logic, not on the CPU (so it’s faster).

- Example in Cisco Switch:
  - A frame arrives for MAC address AA:BB:CC:DD:EE:FF.
  - The data plane checks the MAC table entry that the control plane already learned and immediately sends it out the correct port.

3. How SDN Changes This
  - In traditional networking:
    - Control plane is inside each device (router, switch).
    - We log in to each device to configure it.

  - In SDN (Software Defined Networking):
    - The control plane is centralized in an SDN Controller (e.g., Cisco DNA Center).
    - Devices mainly keep the data plane locally.
    - Controller tells devices how to forward packets (via Southbound APIs like OpenFlow).

- Benefit:
  - Centralized brain = easier automation, faster network-wide changes, single place to apply policy.

- Quick Analogy:
  - Control Plane = The city’s traffic control center deciding routes.
  - Data Plane = The roads where cars actually move.
  - SDN Controller = A central GPS that tells all drivers the best routes in real time.

Southbound APIs vs Northbound APIs

1. Quick Overview
  - In Software-Defined Networking (SDN):
    - Southbound APIs → Connect controller → network devices (switches, routers, firewalls, APs).
    - Northbound APIs → Connect controller → applications / management tools.

  - Think of the controller as the "brain":
    - Southbound = brain talks to the muscles (devices).
    - Northbound = brain talks to the person giving instructions (apps/business logic).

2. Southbound APIs (Device Control)
  - Definition:
    - Protocols and interfaces that let the SDN controller communicate directly with network devices to configure them, gather stats, and control forwarding behavior.

  - Example in CCNA:
    - OpenFlow (most famous)
    - NETCONF, RESTCONF, SNMP, gRPC

  - How it works:
    1. Controller sends instructions to switches/routers (“Send VLAN 20 traffic here”, “Block port 5”).
    2. Switches/routers respond with status and flow statistics.

  - Why we use Southbound APIs:
    - Automates device configuration
    - Pushes policies to multiple devices at once
    - Collects real-time telemetry

  - Analogy:
    - Southbound APIs are like a coach telling players exactly where to move during a match.


3. Northbound APIs (Application Control)
  - Definition:
    - APIs that allow applications or higher-level management systems to communicate with the SDN controller to request network changes or get status updates.

  - Example in CCNA:
    - REST API (most common)
    - GraphQL, WebSocket APIs

  - How it works:
    1. A network management app (like Cisco Prime, monitoring software, or a custom Python script) sends a request to the controller via REST API.
    2. Controller interprets the request and decides what network changes are needed.
    3. Controller uses Southbound API to actually make the change on the devices.

  - Why we use Northbound APIs:
    - Allows integration with automation tools (like Ansible, Python scripts)
    - Lets business apps request network resources dynamically
    - Enables monitoring dashboards

  - Analogy:
    - Northbound APIs are like a team manager telling the coach the game strategy — the coach (controller) then tells the players (devices) what to do via Southbound APIs.

4. Key Differences Table
   Feature                 Southbound API                        Northbound API                        
   Direction               Controller → Devices                  Apps/Services → Controller                
   Purpose                 Device configuration & telemetry      Application integration & policy requests 
   Example Protocols       OpenFlow, NETCONF, RESTCONF, SNMP     REST API, GraphQL                         
   User                    Controller to network hardware        Programmers, network tools                
   Scope                   Low-level device control              High-level business logic                 
   CCNA Relevance          Automates device setup                Allows software to control network        


5. Example Flow in Cisco DNA Center
   1. Northbound API → REST API request from a ticketing system: "Create a new VLAN for HR."
   2. Controller (DNA Center) → processes the request, decides where to apply it.
   3. Southbound API → OpenFlow/NETCONF commands sent to all switches to create VLAN.
   4. Switches apply VLAN instantly without manual CLI work.

API (Application Programming Interface) in the CCNA networking

1. What is an API?
  - In simple words:
    - An API is a set of rules and formats that allows one piece of software to talk to another — like a translator between two systems.
  - In CCNA, APIs are important because they’re how network automation and SDN (Software Defined Networking) tools control and monitor network devices without logging into each one manually via CLI.

2. How it Works in Networking
  - Instead of typing Cisco CLI commands manually on each device, you send requests to a controller or directly to a network device via an API.
  - The API interprets your request, performs the action, and returns results.
  - Example:
    GET /api/v1/network-device
  - Might return:
{
  "hostname": "Switch1",
  "ip": "192.168.1.10",
  "status": "up"
}

3. Why APIs Matter in CCNA
  - In traditional networking:
    - You log into each device → run commands → collect results manually.
  - With APIs:
    - You can automate repetitive tasks
    - Get real-time information from multiple devices at once
    - Integrate networking with other IT systems (security, cloud, monitoring tools)

4. Types of APIs You’ll See in CCNA
  - REST API (Representational State Transfer) → Most common in networking
  - NETCONF / RESTCONF → More device-specific configuration APIs
  - SOAP → Older API format, less common now in Cisco networking

5. CCNA Examples of APIs
  - Cisco DNA Center API → Lets you automate provisioning, monitoring, and troubleshooting.
  - Meraki Dashboard API → Lets you configure Wi-Fi networks, VLANs, and firewall rules remotely.
  - IOS XE RESTCONF API → Lets you directly control a Cisco router or switch.

6. API in SDN Context
  - Northbound APIs: Let applications talk to the SDN controller (high-level policies).
  - Southbound APIs: Let the controller talk to actual switches/routers (low-level configs).

7. Benefits of APIs in Networking
  - Automation → Save time, avoid repetitive tasks
  - Consistency → No human typing errors
  - Scalability → Change 1000 devices at once
  - Integration → Link networking with monitoring/security/cloud platforms

REST(Representational State Transfer API) API


1. What is REST API?
  - REST API = Representational State Transfer API
    - It’s a standard way for applications to communicate over HTTP/HTTPS (the same protocol your web browser uses).

  - Think of REST API as:
    - Client: Sends a request (e.g., "Give me the list of devices")
    - Server: Responds with data (usually in JSON or XML format)


2. How REST API Works in Networking
  - You (or a script) send an HTTP request to a network device or controller (like Cisco DNA Center).
  - The request contains:
    - Method → What you want to do
    - URL/Endpoint → Where you want to do it
    - Headers → Authentication info, content type
    - Body → Data to send (for creating/updating configs)
  - The device responds with status codes and data.


- Common HTTP Methods in REST API
  Method         Purpose                                 Example in Networking   
  GET            Read data                               Get list of switches   
  POST           Create something new                    Create a new VLAN      
  PUT            Update/replace existing data            Change switch hostname 
  PATCH          Update part of an existing resource     Change VLAN name only  
  DELETE         Remove something                        Delete a VLAN          


3. Example: Getting Device List from Cisco DNA Center
- Request:
GET https://dnac.example.com/api/v1/network-device
Headers:
  Content-Type: application/json
  X-Auth-Token: <your_token_here>

- Response (JSON):
{
  "devices": [
    {"hostname": "Switch1", "ip": "192.168.1.10", "status": "up"},
    {"hostname": "Router1", "ip": "192.168.1.1", "status": "down"}
  ]
}


4. Why REST API is Used in Networking
  - Automation: Configure multiple devices without logging in manually.
  - Monitoring: Get real-time health and status reports.
  - Integration: Combine networking data with cloud services, security tools, or reporting systems.
  - Consistency: Apply the same config to many devices without mistakes.


5. REST API in CCNA Topics
  - In CCNA Automation & Programmability, REST APIs are shown as:
    - Northbound APIs → Apps talk to controllers
    - Southbound APIs → Controllers talk to devices
    - Cisco DNA Center → Uses REST APIs for all automation tasks
    - Python + REST API → Often used for scripting automation

JSON and XML

1. What is JSON? (JavaScript Object Notation)
  - Lightweight data format used for storing and exchanging data.
  - Easy for humans to read and write.
  - Easy for machines to parse (especially in automation tools like Python, Ansible, or Cisco DNA Center).
  - Data is written in key-value pairs.
  - Mostly used in modern APIs.

Example — VLAN data in JSON:
{
  "id": 10,
  "name": "Accounts",
  "status": "active"
}

- Where in networking?
  - When Cisco DNA Center or SDN controllers send device information to your automation script.


2. What is XML? (eXtensible Markup Language)
  - Older but still widely used in networking APIs (e.g., NETCONF).
  - Uses tags (like HTML) to structure data.
  - More verbose than JSON.
  - Still machine-readable and human-readable.

- Example — VLAN data in XML:

<vlan>
    <id>10</id>
    <name>Accounts</name>
    <status>active</status>
</vlan>


- Where in networking?
  - Used in NETCONF and SOAP APIs for device configuration.

3. JSON vs XML (Quick CCNA Table)
   Feature             JSON                       XML                      
   Readability         Very simple                More verbose             
   Data Structure      Key-value pairs            Tags with hierarchy      
   File Size           Smaller                    Larger                   
   Speed               Faster to parse            Slower                   
   Common in           REST APIs                  NETCONF, SOAP APIs       
   Best for            Modern web & automation    Legacy & complex configs 


4. CCNA Takeaway
  - JSON = The "modern" way → REST APIs in Cisco DNA Center, Meraki Dashboard, etc.
  - XML = The "classic" way → NETCONF, older API systems, more verbose.

------------------

in CCNA-level REST API learning, you don’t need to be a JSON ninja 🥷, but you do need to know how to look at a basic JSON response and understand what it’s telling you.

1. What is JSON in REST API?
  - JSON = JavaScript Object Notation
  - It’s a lightweight format for sending and receiving data.
  - REST APIs (like Cisco DNA Center) often send back data in JSON instead of plain text.

2. JSON Structure (Key: Value Pairs)
 - A JSON object looks like:
{
  "key": "value"
}


 - Key → The label (e.g., "hostname")
 - Value → The actual data (e.g., "Switch1")

3. Example: Network Device API Output
 - You send:
   GET https://dnac.example.com/api/v1/network-device
 - You might get:
{
  "hostname": "Switch1",
  "ipAddress": "192.168.1.10",
  "status": "reachable",
  "deviceType": "Cisco Catalyst 9300"
}

 - How to read it:
   - hostname → Name of the device → "Switch1"
   - ipAddress → Device’s management IP → "192.168.1.10"
   - status → Device is up and responding → "reachable"
   - deviceType → Model/type of the device → "Cisco Catalyst 9300"

4. JSON with Multiple Devices
  - Sometimes the API sends an array (list) of devices:
[
  {
    "hostname": "Switch1",
    "ipAddress": "192.168.1.10"
  },
  {
    "hostname": "Router1",
    "ipAddress": "192.168.1.1"
  }
]

- Square brackets [ ] → list/array of items
- Curly braces { } → one item’s details

5. Why CCNA cares about reading JSON

In network automation, you may run a script or tool that talks to the router/switch via REST API.

JSON is how you’ll see device configs, status, interface info, errors, etc.

You should be able to pick out the important details quickly.


--------------------

you should know that status codes are the HTTP response codes a server sends back after you make an API request.
They tell you whether your request was successful, had an error, or needs further action.

1. Why status codes matter
  - When a network device or controller (like Cisco DNA Center) receives your REST API request, it responds with:
    - Data (in JSON or XML)
    - A status code that quickly tells you the result

2. Common REST API HTTP Status Codes (CCNA-level)
   Code                         Meaning                        When You See It                                                                   
   200 OK                       Request succeeded              You fetched data successfully (GET), updated config (PUT/PATCH), or deleted (DELETE). 
   201 Created                  Resource created               A new VLAN, interface, or configuration was added successfully.                       
   204 No Content               Success but no data returned   You deleted something, and there’s nothing to show in the response body.              
   400 Bad Request              Request is invalid             Wrong syntax, missing parameter, or invalid data in the request.                      
   401 Unauthorized             Authentication failed          You didn’t provide login credentials or they are incorrect.                           
   403 Forbidden                Access denied                  You’re logged in but don’t have permission for that action.                           
   404 Not Found                Resource doesn’t exist         The endpoint URL or resource name is wrong.                                           
   500 Internal Server Error    Problem on the server side     Device/controller had an unexpected error processing your request. 

3. Example in network automation
  - Let’s say you send a GET request to Cisco DNA Center API to list devices:
    GET https://dnac.example.com/api/v1/network-device
   - If devices are retrieved → 200 OK
   - If you mistyped the URL → 404 Not Found
   - If your API token expired → 401 Unauthorized   

4. Analogy
 - Think of status codes like traffic lights in networking:
   - 200 = Green (All good, go ahead)
   - 400/404 = Yellow (Something’s wrong, fix request)
   - 500 = Red (Stop, problem on the other side)

Ansible, Chef, and Puppet

1. Why these tools exist in networking
  - Traditionally, to configure a Cisco router or switch, you’d:
    - SSH into the device
    - Manually type CLI commands

  - This is fine for 1 or 2 devices, but if you have hundreds of switches and routers, manual configuration is:
    - Slow
    - Error-prone
    - Hard to keep consistent

  - Ansible, Chef, and Puppet are automation tools that let you:
    - Write configuration once
    - Automatically push it to many devices
    - Maintain consistency and compliance

2. The Tools — CCNA-Level View
  - Ansible
    - Agentless — no software needed on the network device.
    - Uses SSH or API calls to configure devices.
    - Configurations are written in YAML (human-friendly format).
    - Very popular in networking (Cisco, Juniper, Arista).
    - Example: Create a YAML file that sets hostname and VLANs on all switches.

  - Chef
    - Requires an agent installed on devices (Chef client).
    - Uses Ruby language to define configurations (called cookbooks and recipes).
    - More common in servers than pure networking, but can work with network APIs.
    - Good for complex infrastructure where you manage servers + network together.

   - Puppet
    - Also agent-based (Puppet agent installed).
    - Uses its own DSL (Domain Specific Language) for configurations.
    - Similar to Chef — more common in IT/server world but supports networking devices.
    - Works well for enforcing compliance (making sure config always matches a template).

3. How They Automate Network Configuration
  - All 3 tools follow the "Define → Push → Verify" model:
    - Define — Write the desired configuration in a file (YAML for Ansible, Ruby for Chef, DSL for Puppet).
    - Push — Tool connects to devices (via SSH, NETCONF, REST API, etc.) and applies changes.
    - Verify — Tool checks that the device is running the intended configuration.

4. CCNA Example — Ansible Configuring Cisco Switch
- YAML playbook to create VLAN 10:

---
- name: Configure VLAN on Cisco Switch
  hosts: switches
  gather_facts: no
  connection: network_cli
  tasks:
    - name: Create VLAN 10
      ios_vlan:
        vlan_id: 10
        name: Sales
        state: present
- Run it once, and VLAN 10 will be created on all switches in the switches group.

NETCONF, RESTCONF, and gRPC

1. Why These Interfaces Exist
   - In the old days, network engineers used CLI over SSH to configure devices — one command at a time.
   - Modern networks use APIs so automation tools and controllers can talk to devices directly and at scale.
   - That’s where these protocols come in — they are interfaces that let software send/receive configurations from routers and switches.


2. The Interfaces in Simple Terms
   Interface      Type                    Data Format                  Transport          Key Points                                           
   NETCONF        XML-based API           XML                          SSH (port 830)     Designed for network devices, works with YANG models 
   RESTCONF       REST API                JSON or XML                  HTTP/HTTPS         Easier for web apps, built on REST principles        
   gRPC           High-performance API    Protocol Buffers (binary)    HTTP/2             Very fast, used for streaming telemetry

- NETCONF
 - What it is: Network Configuration Protocol.
 - How it works:
   - Controller connects to device via SSH.
   - Sends configuration in XML format based on a YANG model.
   - Device replies with XML confirmation.
 - Why we use it: Reliable, transaction-based changes — you can lock config, edit, then commit.
 - Example: Push a VLAN config to 50 switches at once.   


- RESTCONF
 - What it is: RESTful API interface to NETCONF data.
 - How it works:
   - Uses HTTP/HTTPS instead of SSH.
   - Can send/receive config in JSON or XML. 
   - Follows REST API principles (GET, POST, PUT, DELETE, PATCH).
 - Why we use it: Easier for developers since it’s HTTP-based and works well with web tools.
 - Example: A Python script does a PUT request to set an interface IP.   


- gRPC
 - What it is: Google Remote Procedure Call (not Cisco-only).
 - How it works:
   - Uses HTTP/2 for speed.
   - Sends data in Protocol Buffers (compact binary format).
   - Supports streaming telemetry — continuous, real-time updates from the device.
 - Why we use it: High performance, better than SNMP for real-time monitoring.
 - Example: DNA Center collects interface counters from hundreds of routers in real-time.   


3. How Modern Devices Are Programmed Remotely
  - Controller or Automation Tool (Cisco DNA Center, Ansible, custom Python script)
  - Chooses interface (NETCONF, RESTCONF, gRPC)
  - Talks to the network device’s API server
  - Sends commands/configs as structured data (XML/JSON/ProtoBuf)
  - Device applies config and responds     

4. Quick Analogy
  - NETCONF = Sending a formal XML letter via secure courier (SSH) with a lockable box.
  - RESTCONF = Sending a JSON email via secure HTTPS — faster, developer-friendly.
  - gRPC = A live phone call streaming updates continuously in a fast language.


In CCNA-level automation and programmability, protocols like NETCONF, RESTCONF, and gRPC are typically implemented on the network devices (routers, switches, firewalls, etc.) — but they are used and triggered from the controller or automation tool side.


1. Where They Are Installed
 - Network Device (e.g., Cisco Router, Switch)
   - The device’s operating system (like Cisco IOS XE, NX-OS, Junos OS, etc.) has built-in support for these management protocols.
   - You enable and configure the protocol on the device so it can accept remote automation/configuration requests.
   - Example:
     - On a Cisco router, you might run:
       netconf-yang
       restconf
     - to enable NETCONF and RESTCONF services.

 - Controller / Automation Tool
   - Tools like Cisco DNA Center, Ansible, Python scripts, or custom apps send commands via these protocols to the devices.
   - The controller does not need to “install” NETCONF/RESTCONF/gRPC — it just needs to know how to talk to them using libraries or APIs.

2. How It Works
 - Think of it like email:
   - The device is like your email inbox — it needs to be configured to receive messages.
   - The controller is like the person sending the email — it just needs the address and the right protocol to talk to it.
 - Example:
   - Controller sends: “Add a new VLAN” request using RESTCONF over HTTPS.
   - Device receives: The RESTCONF-enabled router/switch reads the JSON/XML payload and updates its configuration.

3. Why This Setup
 - Security:
   - These protocols run on the device, so you can control access with authentication, encryption, and ACLs.

 - Scalability:
   - The controller can manage hundreds of devices at once without logging into each manually.

 - Standardization:
   - Protocols like NETCONF and RESTCONF follow standard data models (YANG), so multiple vendors can be automated in the same way.



4. Quick Example: NETCONF
 - On the Device:
   - Enable NETCONF:
     conf t
     netconf-yang
   - On Controller (Python script using ncclient):
     from ncclient import manager
     with manager.connect(host="192.168.1.1", port=830, username="admin", password="cisco", hostkey_verify=False) as m:
          print(m.get_config(source="running").xml)

YANG (Yet Another Next Generation) is a data modeling language used by protocols like NETCONF and RESTCONF to describe and manage configuration and operational data on network devices.


1. What is YANG?
  - YANG is not a protocol; it’s a modeling language.
  - It defines how data is structured, so both the network device and the management system (controller or automation tool) speak the same data “language”.
  - It ensures that when you ask a device for data or send a configuration, both sides understand the format and meaning.


2. Why YANG is needed
  - Without a common model, every vendor could structure data differently, leading to incompatibility.
  - YANG standardizes what data looks like (e.g., interface name, IP address, status) so automation tools (like Ansible or Cisco DNA Center) can work with different vendors using the same logic.


3. Where YANG is used
  - In NETCONF, YANG defines the data schema for configurations.
  - In RESTCONF, YANG models are exposed over a REST API.
  - In gRPC with gNMI, YANG models are often used to define telemetry and configuration structures.

4. Example
  - Let’s say you want to configure an interface:
    - Without YANG: Every vendor’s XML or JSON format could be different.
    - With YANG:

module example-interface {
    container interface {
        leaf name {
            type string;
        }
        leaf ip-address {
            type string;
        }
        leaf status {
            type enumeration {
                enum up;
                enum down;
            }
        }
    }
}


- This tells any system exactly what fields exist and what values are allowed.


5. Analogy
  - Think of YANG like a blueprint for network configuration data:
  - Blueprint = YANG model (defines structure)
  - Construction = NETCONF / RESTCONF / gRPC (transfers the data)
  - Builders = Controllers / Automation tools (use the model to send/receive config)
